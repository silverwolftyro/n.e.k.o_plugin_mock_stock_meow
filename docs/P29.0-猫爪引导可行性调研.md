# P29.0 · 猫爪引导可行性调研

> 调研范围：插件 `mock_stock_meow` 的 Hosted UI（`ui/panel.tsx`）能否复用宿主 N.E.K.O 主程序那套
> 「猫耳高亮 + 幽灵猫爪光标」新手引导。
> 宿主源码树：`D:\workspace\N.E.K.O\统一开发文档\N.E.K.O-main`（**只读**）。
> 本报告**不含任何代码改动**，只给结论与证据。

## 0. 结论摘要（先给结论）

### 0.1 一句话结论

**不能复用宿主的运行时，但可以复用宿主的美术资源。**
插件的 Hosted UI 跑在一个 **opaque origin（不透明源）** 的 `srcdoc` iframe 里
（`sandbox="allow-scripts"`，**没有** `allow-same-origin`），
宿主的 `window.NekoClickGuide` / `window.TutorialGhostCursorController` / `window.isInTutorial`
**一个都读不到**，`window.parent.X` 会抛 `SecurityError`。【源码证据】

因此推荐 **方案一**（插件内自绘），但**不要用 emoji 重画**——
直接把这 3 张官方 PNG 以 base64 内联进插件自己的资源模块（合计仅 **20 457 字节原始 / 27 280 字符 base64**），
视觉效果与宿主完全一致，且**远在宿主真实的 512 KiB 依赖预算之内**。【实测】

### 0.2 三条硬伤速览

| 硬伤 | 结论 | 关键证据 |
|---|---|---|
| ① 跨域 | **硬伤，成立**。Hosted TSX iframe 是 opaque origin，父窗口全局 API 全部不可达 | `HostedSurfaceFrame.vue:39`、`HostedSurfaceFrame.vue:203-216` |
| ② 资源 | **不是硬伤**。猫爪 PNG 实测只有几十 KB（不是「几 MB」），base64 后仍在预算内；但**不能走宿主 `/static/...` URL** | `ui_query_service.py:45-46`、`plugin/server/routes/frontend.py:21-26`、`main_routers/agent_router.py:471-479` |
| ③ 状态互斥 | **硬伤，成立**。宿主把「正在引导」只写进**主窗口**的 `window.isInTutorial`；插件 iframe 读不到，载荷里也没有任何 tutorial 字段 | `universal-manager.js:3535/4247`、`page-tutorial-manager.js:945/1182`、`ui_query_service.py:1600-1616` |

### 0.3 最终推荐

> **推荐方案一（插件内自绘），美术资源用官方 PNG base64 内联。**
> 理由见 §4.3。若后续仍想上「会动的幽灵猫爪」，建议做 **方案一的增强版**（§4.4 的「方案一+」）：
> 插件内自己实现一个 ~200 行的简化版幽灵光标，**不要**去搬宿主那 1 694 行。

## ① 跨域硬伤

### 1.1 插件的 Hosted UI 到底跑在 iframe 里吗？——跑，而且是**不透明源** iframe

**插件侧声明**（`plugin/plugins/mock_stock_meow/plugin.toml:34-39`）：

```toml
[[plugin.ui.panel]]
id = "market"
title = "拟股喵喵行情"
entry = "ui/panel.tsx"
context = "market"
permissions = ["state:read", "action:call"]
```

`entry = "ui/panel.tsx"` ⇒ 宿主把它解析成 `mode === 'hosted-tsx'` 的 surface。【源码证据】

**宿主侧真正的挂载点**不是 `static/app/app-plugin-views.js`（那条路径是 React 聊天窗口里的
**插件卡片**，见 §1.1.3），而是插件管理器页面里的 Vue 组件
`frontend/plugin-manager/src/components/plugin/HostedSurfaceFrame.vue`：

`HostedSurfaceFrame.vue:32-42`：

```vue
<iframe
  v-else-if="(surface.mode === 'hosted-tsx' || surface.mode === 'markdown') && hostedDocument"
  ref="iframeRef"
  :key="iframeKey"
  :srcdoc="hostedDocument"
  :title="surfaceTitle"
  class="hosted-surface-frame__iframe"
  sandbox="allow-scripts"
  @load="handleLoad"
  @error="handleError"
/>
```

**关键点：`sandbox="allow-scripts"`，列表里没有 `allow-same-origin`。**
按 HTML 规范，sandboxed iframe 若不含 `allow-same-origin`，其文档被强制到
**opaque origin（不透明源）**，对父窗口而言就是**跨源**。

宿主自己的注释也明确写了这件事 —— `HostedSurfaceFrame.vue:203-216`：

```
//   - ``hosted-tsx`` / ``markdown``: iframe is loaded via ``srcdoc=...``. The
//     spec mandates these iframes report ``event.origin === 'null'`` (an opaque
//     origin), so we accept the literal string ``'null'`` as the trusted
//     origin sentinel for srcdoc iframes.
```

> 对比：同一个文件 `HostedSurfaceFrame.vue:22-30` 里 `mode === 'static'`（http URL 载入）
> 的 iframe 用的是 `sandbox="allow-scripts allow-forms allow-popups allow-same-origin allow-modals"`，
> **是**同源的。**但那是 `static` 模式，不是我们的 `hosted-tsx` 模式。**

文档组装处：`frontend/plugin-manager/src/components/plugin/hosted/tsxRuntime.ts:82-99`
（`buildHostedTsxDocument` 返回一段完整 HTML 字符串，交给 `:srcdoc`）。
该文档**没有任何 CSP**（`tsxRuntime.ts:88-99` 只有 `<meta charset>` / viewport / `<style>`），
所以 `data:` 内联图和外部图片都能用。

#### 1.1.1 插件自己也早就知道这件事

`plugin/plugins/mock_stock_meow/ui/assets/avatars.ts` 的头部注释已经写明（该文件第 4-8 行）：

> 「宿主用 `document.createElement` 建元素，画不了 SVG」
> 「相对路径会落到宿主页面（`/ui/plugins/...`）上，宿主**不服务插件目录** ⇒ 必然 404」

这与本报告 §2.4 的实测结论一致。

#### 1.1.2 另一条渲染路径也不能用

`static/app/app-plugin-views.js:239-244` 走的是 React 聊天窗口
（`window.NekoChatWindow.mountPluginContent` → `frontend/react-neko-chat/src/mount-plugin-content.tsx:10-23`
→ `HtmlCardBlock.tsx`）。那条路径的 iframe 是**同源但禁脚本**：

`frontend/react-neko-chat/src/HtmlCardBlock.tsx:7-9`：

```tsx
// Installed plugins supply HTML/CSS, not executable page scripts. The parent
// owns DOM listeners; do not add allow-scripts to this iframe.
const DOCUMENT = '<!doctype html><html><head><meta charset="utf-8"><meta http-equiv="Content-Security-Policy" content="script-src \'none\'; object-src \'none\'; frame-src \'none\'; form-action \'none\'"></head><body></body></html>';
```

`HtmlCardBlock.tsx:275-276`：

```tsx
<iframe ref={frameRef} srcDoc={DOCUMENT} sandbox="allow-same-origin"
  title={block.summary || block.pluginId} style={{ width: '100%', height: 48, border: 0, display: 'block' }} />
```

`sandbox="allow-same-origin"`（无 `allow-scripts`）⇒ **同源但 JS 完全跑不起来**
（CSP `script-src 'none'` 再补一刀）。**结论：这条路径同样无法执行任何插件脚本。**【源码证据】

### 1.2 结论：iframe 内能不能直接 `window.parent.X` / `window.top.X` 调到它？

**不能。**【源码证据 + 推断（依据 HTML 规范）】

1. 插件 Hosted TSX iframe 的 `sandbox` 属性是 `"allow-scripts"`，**缺 `allow-same-origin`**
   ⇒ 文档被强制到 opaque origin（`HostedSurfaceFrame.vue:39` + 同文件 203-216 的官方注释）。
2. opaque-origin iframe 对父窗口是**跨源**的，`window.parent.NekoClickGuide` /
   `window.parent.isInTutorial` / `window.top.TutorialGhostCursorController`
   一律抛 `SecurityError: Blocked a frame with origin "null" from accessing a cross-origin frame`。
3. 即使 `allow-same-origin` 存在也救不了本场景：`window.isInTutorial` 等全局挂在
   **主窗口**上，而插件 iframe 的父窗口是**插件管理器页面**（另一个 origin，见 §2.4.3）。
   `window.parent` 指向插件管理器页，`window.top` 才是主窗口 —— 但 `window.top` 是跨源的，同样读不到。
4. **唯一能用的通道是 `postMessage`**，而宿主的 hosted bridge 只接受三个 method：
   `call` / `refresh` / `parseDocument`
   （`HostedSurfaceFrame.vue:557`、`606`、`611`；另有 `HostedSurfaceFrame.vue:517` 的 cancel）。
   **没有任何 tutorial 相关的 method**。【源码证据】

**硬伤成立。**

### 2.2 插件的依赖上限到底是多少？——宿主源码里的真实数字

**权威来源（不是印象，是代码常量）**：

`ui_query_service.py:1182`：`visit(entry_path, count_bytes=False)` —— entry 自身不计入。

—— **entry 的体积没有显式上限**。

### 2.3 插件现有资源是怎么变成内联 data URI 的？

`ui/assets/avatars.ts` 直接把 PNG 读成 base64 字面量写进 `.ts` 源码，
再由 `ui/panel.tsx:91` 相对导入：

```tsx
import { AVATARS, MEOW_LOAN } from "./assets/avatars"
```

因为 `avatars.ts` 属于 `.ts`（在 `_HOSTED_TSX_CODE_EXTENSIONS` 内），
它会被宿主当作**依赖**加载（`ui_query_service.py:1149-1174` 的相对导入发现逻辑），
所以它的 7 841 字节**计入 512 KiB 预算**。
【源码证据】

### 2.4 结论：几 MB 猫爪 PNG 转 base64 塞进插件超不超限？

**① 体积：不超限，而且余量极大。**【实测 + 源码证据】

- 把 5 张官方图（猫耳×2 + 猫爪 + 幽灵光标×2，base64 共 **60 116 字符**）加进
  `ui/assets/avatars.ts`（或新建 `ui/assets/cat-paw.ts`）：
  该依赖文件变成 ≈ **67 957 字节**，占 512 KiB 预算的 **13.0%**。
- 即便把 `circle-highlight.png` 也带上（121 408 字符），也只有 **23.2%**，仍不超限。
- entry `ui/panel.tsx` 现在 299 193 字节；它**不计入**依赖预算，
  但会被拼进 iframe 文档。加上 UI Kit（`runtime.js` 94 326 + `styles.css` 31 230 字节）
  和依赖，iframe 文档总量约 299 193 + 67 957 + 125 556 ≈ **492 706 字节（≈ 481 KiB）**，

### 3.2 插件 iframe 里能不能读到父窗口的 `window.isInTutorial`？

**不能。**【源码证据 + 推断】

- 同源才能读 ⇒ 但插件 Hosted TSX iframe 是 **opaque origin**（§1.1），**跨源** ⇒ 读父窗口抛 `SecurityError`。
- 更进一步：即使同源也没用 —— `window.isInTutorial` 挂在**主窗口**上，
  插件 iframe 的父窗口是**插件管理器页面**（另一个 origin，§2.4）。
  `window.parent` ≠ 主窗口，`window.top` 才是主窗口，但 `window.top` 跨源。
- `frontend/plugin-manager/src/` 全目录 grep `isInTutorial` ⇒ **零命中**。
  也就是说**插件管理器页面自己都不设置这个标志**——它有自己的一套
  （`frontend/plugin-manager/src/yui-guide-runtime.ts`，见 §3.3）。【源码证据】

### 3.3 读不到的话，有什么替代感知手段？

**逐条查证结果：**

| 候选通道 | 结论 | 证据 |
|---|---|---|
| 宿主给插件的 **context 载荷**里有 tutorial 字段？ | **没有** | `plugin/server/application/plugins/ui_query_service.py:1600-1616`：载荷字段只有 `plugin_id`、`kind`、`surface_id`、`plugin`、`surface`、`state`、`state_schema`、`actions`、`entries`、`config`、`warnings`、`i18n`。**无任何 tutorial 相关字段** |
| Hosted TSX 的 `__NEKO_PAYLOAD` 里有 tutorial 字段？ | **没有** | `frontend/plugin-manager/src/components/plugin/hosted/tsxRuntime.ts:66-80`（`buildPayload`）：`plugin` / `host` / `surface` / `state` / `stateSchema` / `actions` / `entries` / `config` / `warnings` / `locale` / `i18n`。`host` 只有 `{ origin }`（第 69 行） |
| hosted bridge 有 tutorial 查询 method？ | **没有** | `HostedSurfaceFrame.vue:557`（`call`）、`:606`（`refresh`）、`:611`（`parseDocument`）、`:517`（cancel）——只有这四个 |
| 插件面板的 `plugin.toml` 能声明 tutorial 能力？ | **不能** | `plugin.toml` 的 `[plugin.ui.panel]` 只支持 `permissions = ["state:read", "action:call"]`（`plugin.toml:39`）；`plugin.toml` 里没有 tutorial 相关字段 |
| 宿主有 tutorial 状态 HTTP 端点给插件用？ | **没有** | `plugin/server/routes/` 全目录 grep `tutorial` ⇒ 只有 `plugin_install.py:1104` 的 `/plugin/{plugin_id}/ui-api/tutorial/status`，那是**插件安装教程**的进度，且需 `[plugin.install] tutorial_enabled = true`（`plugin_install.py:91-93`），本插件 `plugin.toml` 没有 `[plugin.install]` 段 ⇒ 不可用 |
| 插件后端（Python）能读到浏览器里的 `window.isInTutorial` 吗？ | **不能** | 那是浏览器窗口状态，服务端无感知 |

**唯一存在的「官方插件引导」通道（在插件管理器页面里，但够不到插件 iframe）**：

`frontend/plugin-manager/src/yui-guide-runtime.ts` 就是插件面板页自带的官方引导运行时：

- `yui-guide-runtime.ts:1-5`：直接 import 了**同一套**猫耳/猫爪/幽灵光标 PNG；
- `yui-guide-runtime.ts:3986-3992`：`export function startPluginDashboardTutorial(options)`；
- `yui-guide-runtime.ts:172-182`：`PluginDashboardLocalTutorialStep` =
  `{ targetId, title, body, route?, motion?, action?, waitMs?, allowMissing?, durationMs? }`，
  `motion` 有 `'point' | 'click' | 'ellipse'`（第 170 行）；
- `yui-guide-runtime.ts:3842-3856`：`waitForStepTarget` 用
  `document.querySelector('[data-yui-guide-id="${targetId}"]')` 找目标。

**致命点**：目标查找是**父文档**的 `document.querySelector`，
**进不了 opaque-origin 的插件 iframe**；宿主前端全目录 grep `contentDocument` ⇒ **零命中**，
即宿主**从不**读插件 iframe 的 DOM。所以宿主的官方引导**只能高亮插件 iframe 整块区域**，
无法高亮插件面板里的某个按钮。

同理，`yui-guide-runtime.ts:168` 的 `LOCAL_TUTORIAL_ACTION_EVENT = 'neko:plugin-tutorial:action'`
是在**父窗口** `window.dispatchEvent(new CustomEvent(...))`
（`yui-guide-runtime.ts:3829-3840`），DOM 事件**不跨 document 边界**，插件 iframe 收不到。

### 3.4 结论：插件怎么知道「宿主正在跑教程，我不该抢高亮」？

**现状：插件没有任何可靠的感知手段。**【源码证据】

`window.isInTutorial` 读不到（§3.2），载荷里没有（§3.3），bridge 没有（§3.3），
宿主页面与插件面板页还是两个 origin（§2.4）。

**因此，在「不修改宿主」的前提下，正确的架构决策是：**

> **插件的新手引导必须自己独占一块「视觉层」，并且不能与宿主的高亮层争夺同一块屏幕。**
> 具体做法：
> 1. 插件的引导提示框**画在插件自己的 iframe 内部**（`position: absolute/fixed` 相对 iframe 视口），
>    而不是在宿主页面层。这样它天然被限制在插件面板区域里，
>    宿主的 `click-guide` 遮罩（`static/tutorial/click-guide/mask.js:6-40`，
>    在**主文档** `document.body` 上铺全屏 SVG + 4 块点击拦截 pane）不会与它「重叠抢镜」——
>    二者根本不在同一个渲染层。
> 2. 插件引导**只在「插件面板处于空闲态」时触发**（例如 `onboarding.auto_open === true`
>    且用户 2 秒无操作），并且**一次性**（`onboarding.seen` 已是插件自己写库的状态，
>    见 `__init__.py:9472-9491`），避免与宿主引导在同一时刻抢注意力。
> 3. 插件引导的触发条件**不依赖**宿主的 tutorial 状态（因为拿不到），
>    而是依赖插件自己的状态机 + 用户交互空闲计时。
> 4. 若将来宿主愿意加一个字段，最省事的接口是：在
>    `ui_query_service.py:1600-1616` 的 context 载荷里补一个 `host: { is_tutorial: bool }`
>    （前端 `tsxRuntime.ts:69` 已经把 `host` 透传进 `__NEKO_PAYLOAD`，插件可直接读）。
>    **但这属于宿主改动，不在本次调研范围内。**【推断】

- 完全自治，不依赖宿主任何全局 API、DOM、origin。

### 4.3 推荐哪个？——**推荐方案一**

**理由（按权重排序）：**

1. **可行性决定性**：方案二在「不改宿主」的前提下**不可能做到等价**。
   官方那套是**主文档级**的引导运行时（`window.isInTutorial` + 全屏 SVG 遮罩 + 交互接管 + 跨窗口 handoff），
   插件 iframe 里既没有这些全局、也进不去宿主文档。
   把 `overlay-renderer.js` + `ghost-cursor-controller.js` 搬进 iframe，得到的是
   「一个被裁剪到 iframe 尺寸的、残缺的官方光标」，既不是官方效果，还要背 2 MB 移植负担。【源码证据】
2. **成本收益严重倒挂**：为了一只猫爪搬 70 个文件 / 2.15 MB 宿主代码 + 重写 CSS 定位体系，
   而插件面板本身是个信息密集的行情面板，引导提示最多占一两行。【实测】
3. **风险**：宿主 `static/tutorial/` 是活跃演进的代码（`universal-manager.js` 5 000+ 行、
   `interaction-takeover.js` 会锁 `mouseTrackingEnabled`），**镜像一份进插件 = 永久性的维护分叉**。
4. **方案一有官方兜底**：子代理 B 的 CSS/SVG 自绘方案一定会落地，**不存在「没有引导」的风险**。

**但强烈建议把方案一升级为「方案一+」：**

> **不要用 emoji 🐾 重画，直接 base64 内联官方那 3 张 PNG（猫耳×2 + 猫爪，20 457 字节原始 / 27 280 字符 base64）。**

- 体积只占 512 KiB 依赖预算的 **5.2%**（27 280 / 524 288），几乎无感。【实测】
- 效果**像素级等同宿主官方引导**（同一套美术资源，同一套 CSS 定位参数
  `yui-guide.css:841-864` 的 `top/left/width/height/filter` 可以照抄）。
- **零跨域依赖**：data URI 在 opaque-origin iframe 里完全可用
  （hosted 文档无 CSP，`tsxRuntime.ts:88-99`）。
- 落地方式与插件现有做法完全一致：新建 `ui/assets/cat-paw.ts`，
  照抄 `ui/assets/avatars.ts` 的 base64 常量写法，用 `import { CAT_PAW, CAT_EAR_LEFT, CAT_EAR_RIGHT } from "./assets/cat-paw"` 引入。

**若还想要「会动的幽灵猫爪光标」**（方案二的核心卖点），建议做 **方案一+**：
在插件 iframe 内自己实现一个**简化版**（约 150-250 行 TSX/CSS）：

- 一个 `position: absolute` 的 32×32 元素，`background-image` 用 base64 内联的
